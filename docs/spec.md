# Magpie Agent Vetta：Agent 识别与 Library 能力接入

日期：2026-11-24。
状态：根据已确认需求生成的规格草案；测试边界待确认，尚未发布到 Issue Tracker。本文不代表插件已实现。

## Problem Statement

Vetta 已能通过内置 Magpie 模型预设读取模型，但用户仍需要分别处理 Vetta 使用的 MCP 和 Skills，无法将 Magpie Library 作为这些资源的统一分配入口。

用户需要安装一个独立 Agent 插件，使 Magpie 能识别 Vetta，并将 Library 中选择的 MCP 和 Skills 提供给 Vetta。用户不应为了完成接入而修改或重新编译任一应用，也不应在常规情况下手工查找 Vetta 数据目录。

## Solution

提供一个可独立安装的 Magpie Agent 插件。安装后自动发现并校验 Vetta 的实际资源目录，使 Vetta 出现在 Magpie 的 Agent 和资源分配流程中。用户继续在 Magpie Library 选择哪些 MCP 和 Skills 提供给 Vetta，接管、冲突与撤回遵循宿主原生机制。

最终发布目标包括：用户可在 Magpie 插件发现/搜索界面找到 Vetta Agent 插件，并从界面下载安装。仅支持本地目录安装不满足最终交付。优先采用可自行发布的 GitHub 社区发现路径；官方目录收录作为独立途径，不将维护者是否合并 PR 当成可自行保证的结果。

首版正式验收 Windows 上的 Vetta Desktop。默认目录与自定义目录均纳入发现和验收；只有唯一可信候选才自动采用，无法确定时由用户选择或指定，并在写入前校验。

用户在 Vetta 中仍使用已有的 Magpie 模型预设。插件只适配 Agent 身份和资源分配，不接管模型列表、默认模型或供应商配置。

资源变更后，以 Vetta 新会话读取最新状态为保底要求；尽量使用已有刷新能力使后续轮次生效，允许正在执行的轮次持有原资源快照。

## User Stories

1. 作为 Windows Vetta Desktop 用户，我希望独立安装 Agent 插件，以便接入 Magpie 时无需修改或重新编译应用。
2. 作为 Vetta 用户，我希望 Magpie 的 Agents 页面能识别 Vetta，以便在统一入口管理它的资源。
3. 作为使用默认配置的用户，我希望插件自动找到 Vetta 数据目录，以便无需手填路径。
4. 作为迁移过数据目录的用户，我希望插件检查可用的目录配置和关联信息，以便仍能自动定位我的资源。
5. 作为单独设置 Agent 目录的用户，我希望 MCP 和 Skills 被提供到运行时实际读取的位置，以便避免写到了无效目录。
6. 作为保留多个 Vetta 数据目录的用户，我希望系统区分当前目录与旧目录，以便不会误写旧配置。
7. 作为存在多个有效候选目录的用户，我希望可以选择目标，以便资源被分配到我想使用的实例。
8. 作为自动发现失败的用户，我希望可以指定并校验目录，以便继续完成接入。
9. 作为未安装或尚未初始化 Vetta 的用户，我希望看到准确的发现状态，以便不被虚假的接入成功误导。
10. 作为 Magpie Library 用户，我希望在原有界面选择是否向 Vetta 分配 MCP，以便沿用熟悉的管理方式。
11. 作为 Vetta 用户，我希望实际调用被分配的 stdio MCP 工具，以便使用本机提供的能力。
12. 作为 Vetta 用户，我希望实际调用被分配的 HTTP MCP 工具，以便使用远程或路由服务的能力。
13. 作为使用鉴权 HTTP MCP 的用户，我希望所需请求头正确传递，以便服务器鉴权能够正常工作。
14. 作为使用 Magpie MCP router 的用户，我希望 Vetta 能通过 router 发现并调用获分配的工具，以便集中管理服务器。
15. 作为希望保留直接连接的用户，我希望 router 关闭或资源设为直接分发时仍能使用对应 MCP，以便沿用 Magpie 提供的选择。
16. 作为取消 MCP 分配的用户，我希望新会话不再从该分配获得工具，以便资源可见性反映 Library 的最新选择。
17. 作为 Magpie Library 用户，我希望在原有界面为 Vetta 分配 Skills，以便统一维护能力包。
18. 作为 Vetta 用户，我希望被分配 Skill 的名称和描述能够被发现，以便知道何时使用该能力。
19. 作为 Vetta 用户，我希望能加载 Skill 的完整正文，以便 Agent 执行完整指令。
20. 作为使用带附属资源 Skill 的用户，我希望相对资源能够被读取，允许执行的脚本能够按 Vetta 既有权限运行，以便能力包可实际工作。
21. 作为使用 Skill router 的用户，我希望 Vetta 能从路由入口按需读取对应 Skill，以便保留 router 降低初始提示开销的效果。
22. 作为希望直接分发 Skill 的用户，我希望 router 关闭或单项直接分发时仍能加载 Skill，以便遵循 Library 的选择。
23. 作为取消 Skill 分配的用户，我希望新会话不再从该分配获得该能力，以便撤回操作有可观察的效果。
24. 作为已有自有资源的用户，我希望接管和冲突遵循 Magpie 原生规则，以便无需理解插件新增的另一套资源管理逻辑。
25. 作为使用多个 Agent 的用户，我希望 Vetta 资源入口独立于其他 Agent 的共享入口，以便分配给 Vetta 的行为不会无意改变其他 Agent 的资源。
26. 作为已有模型设置的用户，我希望插件保持这些设置不变，以便继续使用 Vetta 已有的 Magpie 模型能力。
27. 作为正在执行任务的用户，我希望资源更新不会强制替换当前轮次的工具或技能快照，以便在途任务保持一致。
28. 作为创建新会话的用户，我希望读取更新后的资源状态，以便能够确定地使用新增资源或观察撤回结果。
29. 作为取消分配的用户，我希望撤回只按宿主语义影响该分配，以便不会误以为其他项目配置或独立来源也已被删除。
30. 作为准备卸载的用户，我希望知道 Library 撤回与插件卸载的区别及正确顺序，以便避免遗留资源。
31. 作为遇到资源不可用的用户，我希望得到可操作的诊断，以便区分目录未确认、资源未分配、Vetta 权限和服务器连接问题。
32. 作为安装插件的用户，我希望可见开关和连接状态能正常工作，以便不会遇到仅声明成功、实际操作立即报错的接入。
33. 作为选择兼容版本的用户，我希望支持说明基于实际验证，以便不会将静态源码兼容误认为已通过运行验证。
34. 作为尚未安装插件的用户，我希望在 Magpie 插件发现/搜索界面找到 Vetta Agent 插件，以便无需寻找本地源码目录。
35. 作为找到插件的用户，我希望在界面查看其身份和说明并下载安装，以便直接开始使用统一管理的资源。
36. 作为安装公开发布版本的用户，我希望下载结果与通过验收的插件版本一致，以便获得可复现的安装体验。

## Implementation Decisions

### 已确认的边界

- 交付为独立 Magpie Agent 插件，首版验收 Windows Vetta Desktop。
- 最终通过 Magpie 插件发现/搜索界面可下载安装，并能识别为 Agent 类型。发布渠道优先使用公开 GitHub 仓库加 magpie-plugin topic 的社区发现机制；可由 GitHub 安装或使用有效 npm 分发来源。是否发布 npm 包由实际渠道要求决定，不为 GitHub 路径增加无依据的强制条件。
- 使用 Magpie 的 Agent 插件接口声明身份与 Library 入口，资源分配复用 Library 机制。
- 保持 Vetta 自带的 Magpie 模型接入；插件不新增模型代理、不维护另一份模型目录、不改默认模型。
- 目录发现优先自动完成，覆盖默认目录、自定义数据根和自定义 Agent 根。唯一可信候选自动采用，未找到或存在歧义时提供用户选择/指定并校验的兜底。
- 使用 Vetta 实际读取的专属资源入口，区分安装目录、数据根、Agent 根和项目目录。对用户目录环境、Vetta 覆盖配置及能可靠取得的运行/启动关联信息分别处理。
- 发现结果必须有身份及关联依据；文件夹存在、发现同名文件或候选搜索顺序本身都不足以证明它是当前目录。未确认目标时不进行资源写入。
- Magpie 进程可见的环境与 Vetta 实际环境可能不同，不能仅展开前者的变量就声明完成了路径发现。
- MCP 由 Magpie 原生分发或通过其 router 提供；HTTP 连接要保留显式传输类型、地址和鉴权请求头。SSE 的协议模式限制按受支持版本验证，不由 HTTP 的结构匹配推导其已兼容。
- Skills 由宿主按链接或副本机制提供，正文、相对资源和获准脚本需在 Vetta 既有权限边界内工作。不会为了让脚本通过而绕过 Vetta 的审批。
- 同时验收 MCP router 和 Skill router 的启用、关闭及资源直接分发场景；不以更改用户的全局 router 设置来掩盖兼容问题。
- Skill router 的内部隐藏目录无需被递归发现为独立 Skills；正确目标是让可见入口按正文路径引导 Vetta 按需加载。
- 资源增加或撤回后，新会话读取最新分配状态为保底。后续轮次刷新尽量复用 Vetta 已有机制；当前轮次不要求中途切换资源或即时终止已开始的调用。
- 同名 MCP 的核心字段接管、Skill 冲突取舍与撤回均遵循 Magpie 原生语义；不增加插件独有的“全部保留”或“全部覆盖”策略。
- 原生项目配置与全局配置可能合并，其他独立来源也可能提供同名能力。取消一项资源分配只撤回该分配，不能将其他来源仍可见误判为插件撤回失败。
- 卸载说明必须区分资源撤回和 Agent 插件移除。当前源码未证明移除插件会自动清除 Library 分发；首版按先在 Library 撤回并确认、再卸载验证和说明，不承诺未经证明的自动恢复。
- 支持版本、开关含义与诊断须反映真实能力，不能将候选方案或静态匹配包装为完整兼容承诺。

### 已知约束与待验证的实现

- 宿主注册契约要求连接配置，并至少具有模型字段或连接函数；当前没有原生只含 Library 声明的插件形态。空连接函数不是可接受实现，因为用户启用时会失败。
- 插件独立维护连接状态是候选适配方案，不是已通过验证的架构决定。需确认该方式能在宿主生命周期内提供清晰且可用的操作，又不接管 Vetta 模型配置。
- 静态描述是否足以表达自动发现后的动态路径尚待验证。若需要运行时，只在独立插件内部补足，并维持原生 Library 作为分配来源。
- 如现有插件接口无法在这些约束内完成接入，实施应停在可复现的限制说明，并重新讨论方案；不能默认修改或要求用户重新编译上游。
- 不预先指定轮询频率、状态文件布局、目录选择算法或界面形式。具体实现服从已确认的行为及验收，不以实现便利删去自动发现或 router 场景。

## Testing Decisions

### 测试边界与原则

建议以一个主要用户流程边界验收：独立安装插件，Magpie 识别目标，用户在 Library 分配资源，真实 Vetta Desktop 新会话加载并使用，随后撤回并在新会话观察结果。该测试边界待用户确认；首版业务需求已确认，不重新访谈。

测试观察可见行为、实际工具执行与资源加载结果、受影响配置的范围；不把“描述对象包含某字段”“私有方法被调用”或实现自身生成的预期对象作为主要正确性证据。

测试对象是插件在宿主中的完整行为及其与 Vetta 资源运行时的契约。为确定性和隔离，仅在外部边界使用临时用户目录、可控启动/环境证据、假 stdio/HTTP MCP server 和最小 Skill 包，不为每个内部模块增加测试接口。

真实 Desktop 是最终验收宿主；Vetta 共享加载器或 RPC 宿主可以辅助自动化验证，但不能以其通过替代 Windows Desktop 验收。模型规划具有非确定性，确定性测试优先直接验证运行时工具/资源边界，另外执行真实会话使用的烟雾验收。

### 验收矩阵

| 编号 | 场景 | 必须观察到的行为 |
| --- | --- | --- |
| A1 | 安装到受支持的 Magpie，存在已初始化 Vetta | 识别 Vetta，Library 可对其分配资源，可见开关可正常操作 |
| A2 | 默认数据目录 | 自动找到可信目标，用户无需手填路径 |
| A3 | 自定义数据根或 Agent 根 | 自动使用有充分证据的候选，资源到达实际 runtime 入口 |
| A4 | 环境不一致、旧目录残留、多个有效候选或无目标 | 不写入猜测目标；明确需要用户选择/指定的状态；指定后重新校验 |
| A5 | 直接分发 stdio MCP 和 HTTP MCP | Vetta 新会话真实调用工具，参数与返回结果匹配测试 server；HTTP 鉴权头实际到达 server |
| A6 | MCP router 启用与关闭 | 启用时可发现并调用获分配工具；关闭/直接分发时按 Library 选择工作，不调用未分配的测试工具 |
| A7 | 普通 Skill 与附属资源 | 名称描述可发现，正文可加载，相对资源内容正确，最小获准脚本在权限允许时可运行 |
| A8 | Skill router 启用与关闭 | 路由入口可按需读取对应 Skill；不将内部全部描述重复注入；直接分发可正常加载 |
| A9 | 同名自有资源、用户编辑、项目覆盖/合并 | 表现与宿主和 Vetta 已核实的原生语义一致；未分配的其他资源不被插件改写 |
| A10 | 新增与撤回资源 | 新会话反映最新状态；隔离其他来源后，已撤回分配不再提供该能力；不要求中断在途调用 |
| A11 | 已有模型设置与其他 Agent | 插件接入、分配、撤回不改变模型设置，也不通过共享目录意外更改其他 Agent 的分配 |
| A12 | 先撤回，再关闭或卸载插件 | 撤回符合宿主机制，记录遗留/保留内容及原因；不声称自动恢复未验证的原有条目 |
| A13 | 重复启用、重复分配、重复刷新 | 可见结果稳定，不累积重复 Agent 或重复资源入口；无需重置真实用户配置 |
| A14 | 无效配置、权限拒绝或 server 不可用 | 报告对应边界的失败，不伪造已接通/工具已执行；诊断不输出密钥或工具正文 |
| A15 | 插件市场发现和下载 | 发布后在受支持 Magpie 插件发现/搜索界面找到 Vetta Agent 插件，显示正确身份与版本/来源，点击安装成功，再完成 Agent 识别和资源使用烟雾验收 |

router 模式和直接分发模式均是首版验收项；仅配置生成成功不足以判定 A5–A8 通过。取消分配场景使用隔离资源，避免其他项目或共享来源使结论失真。

### 可复用的先例

- Magpie 已有 Agent 插件注册、connect-only 和 Library Agent target 的测试先例，可借用临时用户目录和宿主装载方式。
- Magpie 已有 MCP 分发、router 和 Skill 冲突/撤回测试先例，可借用假 server 与归属判定场景。
- Vetta 已有 MCP 配置兼容、动态 HTTP headers、Skills 发现和路由测试先例，可借用资源 fixture 和结果断言。
- 社区 Trae Agent 插件已有隔离用户目录中的宿主验收思路；可参考测试组织，不继承其模型桥接、账号或模型同步逻辑。

当前阶段只形成测试决策，没有新增测试代码，也未运行上游测试。上述先例来自源码调研，应在实施时固定版本并核实实际入口。

## Out of Scope

- 启动 Vetta、托管其进程或管理任务执行生命周期。
- 重复实现模型发现、模型目录同步、默认模型设置和供应商配置。
- 会话统计、调用记录、历史导入；这些保留到后续阶段。MCP 工具实际执行仍在首版范围。
- 首版承诺 CLI、macOS、Linux 已正式兼容。
- 修改或重新编译 Magpie、Vetta；若成为必要条件，需说明限制并重新决策。
- 插件独有的资源分配界面、与宿主不同的冲突政策。
- 资源写入后立即生效、正在执行轮次中途替换、取消分配即时终止在途调用。
- 保证自动找到磁盘上任意位置的数据，或按首次扫描命中不经校验直接写入。
- 未验证的卸载自动清理、自动恢复接管前同名 MCP 的承诺。
- 在本次规格工作中编写实现、安装插件或修改真实 Vetta/Magpie 用户配置。
